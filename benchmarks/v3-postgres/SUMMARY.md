## Closed model — what N concurrent clients experience

| run | VUs | iter/s | req/s | p50 ms | p95 ms | p99 ms | p95 served ms | failed | 5xx |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| v3-baseline | 5 | 1.04 | 4.76 | 2.49 | 70.85 | 82.03 | 70.85 | 0.00% | 0.00% |

**† = timeout-censored. Do not quote these as latency.** In a row with any
abandoned request, every quantile at or past the abandonment point equals the
client timeout rather than a measured server response time, so `p95` there says
"the client gave up", not "the server took this long". `p95 served` is the p95
over `http_req_duration{expected_response:true}` — the requests that actually
got an answer — and is the only latency figure on a censored row that means
anything. `iter/s` is the honest capacity number: one iteration is one
/health + one sign-in + one users list + one user-by-id.

The blended p95 above is reported for completeness but is the *least*
useful number here: it mixes a no-I/O health check with a bcrypt signin
and an unbounded table scan. Use the per-endpoint table below.

## Failure attribution — what "failed" actually was

| run | VUs | requests | answered | abandoned (status 0) | 4xx | 5xx | 429 | 403 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| v3-baseline | 5 | 96 | 96 | 0 | 0 | 0 | 0 | 0 |

`abandoned` is k6 status 0: no HTTP response was received at all. It is not an
application error — the app never got the chance to return one. A run whose
failures are entirely status 0, with 4xx/5xx/429/403 all zero, is a run where
offered load exceeded capacity and the load generator timed out waiting. The
fix for that is capacity or a smaller offered load, never error handling.

`failure-attribution.txt` splits status 0 by k6 `error_code`, taken from the
per-request `--out json` streams: **1220** (`read: connection reset by peer`,
an RST from the server side, clustered at 15001 ms) and **1050** (`request
timeout`, k6 giving up at its 60 s default). Regenerate it with
`node benchmarks/scripts/attribute-failures.mjs`.

`GET /api/users` is measured with an admin session (see `setup()` in
`benchmarks/k6/baseline.js`). Without one, `authorize('admin')` rejects the
request before the controller runs and the unbounded scan is never executed —
the number would be the cost of a middleware rejection, not of the query.

## Reproduce

```bash
cp .env.bench.example .env.bench
git checkout 435aa10
PHASE=v3 ./benchmarks/scripts/run-phase.sh
node benchmarks/scripts/report.mjs --phase v3 --dir benchmarks/v3/results --out benchmarks/v3-postgres/SUMMARY.md \
     --compare benchmarks/v0-baseline/results
node benchmarks/scripts/attribute-failures.mjs --dir benchmarks/v3/results
```

Every level set is env-overridable, so a quick partial probe needs no code
change:

```bash
VU_LEVELS="5 10" REALISTIC_LEVELS="" SAT_RATES="10" \
  PHASE=v3 ./benchmarks/scripts/run-phase.sh
```

The default frozen-instrument matrix is all seven levels because the report
needs both sides of the knee. Extrapolated from the Phase 0 run at ~4.4 minutes
per closed-model run including cool-down, the defaults come to roughly 50
minutes.
