`abandoned` is k6 status 0: no HTTP response was received at all. It is not an
application error — the app never got the chance to return one. A run whose
failures are entirely status 0, with 4xx/5xx/429/403 all zero, is a run where
offered load exceeded capacity and the load generator timed out waiting. The
fix for that is capacity or a smaller offered load, never error handling.

`failure-attribution.txt` splits status 0 by k6 `error_code`, taken from the
per-request `--out json` streams: **1220** (`read: connection reset by peer`,
an RST from the server side, clustered at 15001 ms) and **1050** (`request
timeout`, k6 giving up at its 60 s default). Regenerate it with
`node benchmarks/scripts/attribute-failures.mjs`.

`dropped` is k6 `dropped_iterations`: requests the load generator could not
start on schedule because the system was not keeping up. Any value above zero
is the saturation point. A closed-model test cannot surface this — when the
server slows, closed-model VUs slow with it and the offered load silently
drops (coordinated omission).

**Scope caveat — this is not the application's capacity.** `saturation.js`
hits `GET /api`, which returns a static object with no database access and no
bcrypt, and `run-baseline.sh` starts these runs with `BENCH_BYPASS_SECURITY=1`
so the middleware is skipped too. What these rows measure is Express routing
throughput on the pinned CPU, which is why nothing was ever dropped. The
capacity of the real endpoint mix is the `iter/s` column of the closed-model
table, an order of magnitude lower. Pointing this scenario at the same mix as
`baseline.js` is what would turn it into an actual knee measurement.

This is why both variants are run. Attributing the whole baseline p95 to
application code, when a third-party network hop was inside the request
path, would overstate every later improvement.

Note what the 403 column of the failure table shows: **zero**. The as-built
sliding window at `src/middleware/security.middleware.js:25` runs in `LIVE`
mode with a limit of 5 requests/minute for `guest`, yet nothing was ever
throttled — because `ARCJET_KEY` is empty for the baseline and an errored
decision is treated as allow (finding F-07). Arcjet was in the request path
costing latency, but it was never enforcing anything. Supplying a working key
would not fix these runs, it would end them: at 5 requests/minute per IP,
every VU shares one source address and the whole matrix becomes 403s.

## Reproduce

```bash
cp .env.bench.example .env.bench
git checkout v0-baseline
PHASE=v0 ./benchmarks/scripts/run-phase.sh
node benchmarks/scripts/report.mjs --phase v0 --dir benchmarks/v0-baseline/results --out benchmarks/v0-baseline/SUMMARY.md
node benchmarks/scripts/attribute-failures.mjs --dir benchmarks/v0-baseline/results
```

Every level set is env-overridable, so a quick partial probe needs no code
change:

```bash
VU_LEVELS="5 10" REALISTIC_LEVELS="" SAT_RATES="10" \
  PHASE=v0 ./benchmarks/scripts/run-phase.sh
```

The default frozen-instrument matrix is all seven levels because the report
needs both sides of the knee. Extrapolated from the Phase 0 run at ~4.4 minutes
per closed-model run including cool-down, the defaults come to roughly 50
minutes.
