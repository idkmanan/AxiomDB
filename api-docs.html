Overview

The Acquisitions API is a production-ready distributed backend demonstrating enterprise patterns: Redis-backed distributed rate limiting, refresh token rotation, optimistic locking, idempotency keys, and Kafka event streaming with transactional outbox.

Built over 7 measured phases with 50+ documented findings. Performance improved from 695ms p95 (v0) to 6ms p95 (v7) — a 99.1% latency reduction.

Authentication

The API uses JWT access tokens (15min TTL) with opaque refresh tokens (30 day TTL). Access tokens are sent in cookies on every request. Refresh tokens are scoped to /api/auth only and support rotation with reuse detection.

Authentication Flow

1. POST /api/auth/sign-up or /api/auth/sign-in
   → Returns user object + sets two cookies:
     • token (access JWT, domain-wide)
     • refresh_token (scoped to /api/auth)

2. Include cookies on subsequent requests
   → Middleware validates access token

3. When access token expires (15min):
   POST /api/auth/refresh
   → Rotates refresh token, mints new access token

4. POST /api/auth/sign-out
   → Revokes access token (denylist) + kills refresh family

Rate Limiting

Redis Authentication endpoints are heavily rate limited (keyed by IP, fails closed). Authenticated endpoints use per-role limits (keyed by user ID, fails open without Redis).

Health & Status

GET /health ▼

Liveness probe. Answers from in-process state only, with no dependency check. Returns 503 when shutting down.

Response 200

{
  "status": "OK",
  "timestamp": "2026-09-09T10:05:32.123Z",
  "uptime": 3600.45
}
GET /ready ▼

Readiness probe. Checks Postgres connection (required) and reports Redis status (optional). Returns 503 during shutdown or when database is unreachable.

Response 200

{
  "status": "READY",
  "ready": true,
  "db": { "ok": true, "latencyMs": 2.4 },
  "pool": { "total": 10, "idle": 8, "waiting": 0 },
  "redis": { "ok": true, "latencyMs": 1.2 },
  "rateLimitStore": "redis"
}
GET /metrics ▼

Prometheus-format metrics endpoint. Exposes RED metrics (Rate, Errors, Duration), pool saturation, event-loop lag, and rate limit state. Protected by METRICS_TOKEN when set.

Headers

Authorization string
Bearer token (if METRICS_TOKEN is set)

Authentication Rate Limited

POST /api/auth/sign-up ▼

Create a new user account. Returns user object and sets authentication cookies. New users always get role "user" — the role field is never accepted from the request body (finding F-23).

Request Body

name string required
User's full name (2-100 chars)
email string required
Valid email address
password string required
Minimum 8 characters

Response 201

{
  "message": "User created successfully",
  "user": {
    "id": 42,
    "name": "Alice Johnson",
    "email": "alice@example.com",
    "role": "user"
  }
}

Try it out

POST /api/auth/sign-in ▼

Authenticate with email and password. Returns user object and sets authentication cookies (access token + refresh token).

Request Body

email string required
password string required

Response 200

{
  "message": "Sign in successful",
  "user": {
    "id": 42,
    "name": "Alice Johnson",
    "email": "alice@example.com",
    "role": "user"
  }
}
POST /api/auth/refresh ▼

Redis Required Rotate refresh token and mint new access token. Detects reuse and revokes family on replay. User is re-read from database (authorization stays at most 15min stale).

Response 200

{
  "message": "Session refreshed",
  "user": {
    "id": 42,
    "name": "Alice Johnson",
    "email": "alice@example.com",
    "role": "user"
  },
  "expiresIn": 900
}
POST /api/auth/sign-out ▼

Revoke access token (denylist by jti) and kill refresh family. Best-effort, always returns 200. Clears cookies regardless of revocation success.

Response 200

{
  "message": "Sign out successful",
  "revoked": {
    "accessToken": true,
    "refreshFamily": true
  }
}

PUT /api/deals/:id ▼

Update deal with optimistic locking. Provide expected version via If-Match header or version in body. Returns 409 with current version on conflict.

Request Headers

If-Match string
Entity tag with expected version: W/"3"

Request Body

version integer
Expected version (alternative to If-Match). Cannot disagree with header if both present.
title string
company string
amount_cents integer
currency string

Response 200

{
  "message": "Deal updated",
  "deal": {
    "id": 101,
    "version": 4,
    ...
  }
}

Response 409 (Version Conflict)

{
  "error": "Conflict",
  "message": "Deal was modified (expected version 3, current is 5)",
  "code": "VERSION_CONFLICT",
  "currentVersion": 5,
  "requestId": "req_abc123"
}
POST /api/deals/:id/stage ▼

Advance deal stage. Validates state machine transitions. Not idempotent — advancing twice is two different outcomes, second returns 409.

Request Body

to string required
Target stage (must be valid transition from current)

Response 200

{
  "message": "Deal advanced to won",
  "deal": {
    "id": 101,
    "stage": "won",
    "version": 5,
    ...
  }
}

Response 409 (Illegal Transition)

{
  "error": "Conflict",
  "message": "Cannot advance from 'lead' to 'won'",
  "code": "ILLEGAL_STAGE_TRANSITION",
  "currentStage": "lead",
  "allowedStages": ["qualified", "lost"],
  "requestId": "req_abc123"
}
DELETE /api/deals/:id ▼

Delete deal. Idempotent (second delete returns 404). Non-admins can only delete own deals.

Response 200

{
  "message": "Deal deleted successfully"
}
