8 ADRs Architectural Decisions

ADR 0001 Measure the unmodified system before changing it
Status: Accepted • Date: Sep 1, 2026 • Phase: 0

Context

The project's goal is to support claims of the form "reduced p95 latency from X to Y at N concurrent clients." The credibility of such a claim rests entirely on how X was obtained.

Decision

Baseline first.

Rationale

A retro-baseline is not falsifiable. Flags do not fully revert a change - the schema, connection handling, and code paths differ from what actually existed before - so the reconstructed "before" is an estimate presented as a measurement.

ADR 0002 Own the failure policy
Status: Accepted • Date: Sep 1, 2026 • Phase: 1

Context

With no ARCJET_KEY and no network egress, aj.protect() returns an ERROR decision and security.middleware.js allows the request - it checks isDenied() only, never isErrored().

Decision

Explicit fail-open/fail-closed policy per route.

Consequences

Redis-backed limiter stays installed, its commands fail fast (enableOfflineQueue: false), and the per-route policy decides: auth endpoints fail CLOSED with 503, reads fail OPEN and are logged and counted.

ADR 0003 In-process limiter then Redis
Status: Accepted • Date: Sep 1, 2026 • Phase: 1

Context

Phase 1's first fix was to throw in production for missing JWT_SECRET, but the literal itself stayed, creating two problems: a committed credential-shaped constant and reliance on the fallback.

Decision

Remove the hardcoded fallback and generate ephemeral secret in development.

Consequences

Nothing secret-shaped is committed. Developers who want sessions to survive restart must set JWT_SECRET.

ADR 0004 One database driver
Status: Accepted • Date: Sep 4, 2026 • Phase: 3

Context

v0 constructed new Pool({ connectionString }) and inherited node-postgres defaults: max=10, connectionTimeoutMillis=0 meaning "queue forever" rather than "no timeout".

Decision

Use connectionTimeoutMillis=5000 and idleTimeoutMillis=30000 with PG_POOL_MAX=20.

Consequences

Prevents connection queuing forever and enables proper pool pre-warming to avoid connect timeouts under load (F-37).

ADR 0005 Drop TypeScript migration
Status: Struck • Date: TBD • Phase: 2

Context

Phase 2 planned TypeScript migration, but team evaluated costs vs benefits.

Decision

Deliberately struck - not deferred.

Rationale

TypeScript migration would add complexity (build step, type definitions) without sufficient safety benefits for this codebase's complexity and test coverage.

ADR 0006 Hand-written metrics
Status: Reduced • Date: Sep 5, 2026 • Phase: 6

Context

Phase 6 planned full observability with OpenTelemetry, Grafana, and Prometheus integration.

Decision

Reduced scope to hand-written /metrics endpoint carrying essential signals.

Rationale

The signals needed (RED metrics, pool saturation, event-loop lag, outbox depth) can be exposed simply without OTel complexity. Avoids vendor lock-in and operational overhead.

ADR 0007 The outbox, and no dual writes
Status: Accepted • Date: Sep 5, 2026 • Phase: 5

Context

POST /api/deals must persist deal and tell system about it. Direct approach has two systems in one request handler: database insert and Kafka send.

Decision

Write event to outbox table in same transaction as domain change. Separate publisher polls and sends to Kafka.

Consequences

Four supporting decisions: stable event ID from writer, FOR UPDATE SKIP LOCKED, keying by aggregate, consumer claims by inserting handler record.

ADR 0008 HPA on CPU
Status: Accepted • Date: Sep 5, 2026 • Phase: 7

Context

Phase 7 planned Kubernetes deployment with autoscaling.

Decision

Horizontal Pod Autoscaler based on CPU utilization.

Consequences

Enables automatic scaling based on load, demonstrated in Phase 7 failure drills and benchmark matrix.

Key Insights What the Numbers Mean

Blended vs Per-Endpoint Metrics: The reported p95 mixes health check (no I/O), sign-in (bcrypt), and users list (unbounded scan). Always look at per-endpoint breakdown for accurate performance characterization.
The v0→v7 Journey: From 695ms p95 to 6ms p95 represents fixing the fundamental bottlenecks: unbouded scans → keyset pagination, connection timeouts → proper pool configuration, rate limiting 403→429, and more.
Capacity vs Latency Trade-off: v7 shows higher error rate at 100 VUs (4.27% vs 2.79%) but 58× higher throughput - the system handles more load before failing, which is the goal of scaling.
