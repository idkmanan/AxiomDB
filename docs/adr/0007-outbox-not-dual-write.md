# ADR 0007 — The outbox, and no dual writes anywhere

**Status:** accepted
**Date:** 2026-09-05
**Phase:** 5 (Kafka & outbox)

## Context

`POST /api/deals` has to do two things: persist the deal and tell the rest of the system
about it. Written directly, that is two systems in one request handler:

```js
await db.insert(deals)…      // Postgres
await producer.send(event)   // Kafka
```

There is no ordering of those two lines that is correct. Publish first and a database
failure announces a deal that does not exist. Write first and a broker failure — or a
pod killed between the two, which is not exotic during a rolling deploy — loses the
event silently, after the client already has its 201. `try/catch` does not help, because
the failure can happen *between* the statements.

## Decision

Write the event to an `outbox` table in the **same transaction** as the domain change.
A separate publisher process polls the table and sends to Kafka.

Four supporting decisions, each of which is a place this pattern is usually got wrong:

**The event id is generated by the writer**, not the broker, so it is stable across
every redelivery. That stability is the only thing that makes consumer deduplication
possible.

**The publisher claims with `FOR UPDATE SKIP LOCKED`** and holds the transaction across
the send. A publisher that dies mid-send releases its rows and the next attempt
re-sends them — at-least-once, by construction.

**The partition key is `<aggregate_type>:<aggregate_id>`.** Kafka orders within a
partition and not across. A null key spreads events round-robin, so a consumer can see
`deal.stage_advanced` for a deal it has never been told about. Keying by aggregate is
exactly as much ordering as the domain needs; keying by nothing, or by event type, is
either too little or a single partition.

**The consumer claims each event by inserting `(consumer_group, event_id)` inside the
handler's transaction.** At-least-once delivery, exactly-once *effect*. Recording "I
handled this" anywhere else — Redis, or a second transaction — reintroduces the dual
write inside the fix for the dual write.

## Consequences

**Gained.** No lost events and no phantom events, and the API is fully available while
the broker is down: writes succeed, the backlog grows, and it drains on its own.
`scripts/events/outbox-drill.mjs` asserts exactly that, because it is invisible in
normal operation — with the broker up, an outbox and a dual write look identical.

**Cost.** Latency: the event is published after the commit, not during it (one poll
interval, 250 ms by default). Write amplification: every domain write is two inserts.
Table growth: published rows accumulate until something trims them, which is a retention
job this project has not written — `outbox_pending` is bounded by the partial index, but
the heap is not, and that is a known gap rather than an oversight.

**Constraint imposed on everything downstream.** Consumers must be idempotent. That is
not a caveat, it is the contract, and it is why `processed_events` exists and why the
handlers take a transaction rather than a database.

**Alternatives considered.** Debezium/CDC reads the WAL and needs no outbox table, but
it publishes *row changes* rather than domain events — the consumer then reverse-engineers
intent from a diff, and a schema change becomes a breaking API change for every consumer.
Kafka transactions plus a Postgres transaction cannot be made atomic with each other
either, so that is the same dual write with more moving parts.
